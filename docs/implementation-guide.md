# Implementation guide

How the labs are built, in the order you would build one yourself. Each step names the files to read. Everything runs offline; the Azure seam is a set of stubs selected by `LAB_MODE=azure`.

## 1. Set up

```bash
python -m venv .venv && . .venv/bin/activate
pip install -e ".[dev]"
pytest -q                      # every test, offline
python scripts/run_all_evals.py
```

The root `pyproject.toml` installs `shared/labcore` and the five lab packages, so a lab imports `labcore` like any library.

## 2. Start from the shared layer

Read [components/labcore.md](components/labcore.md) first. A lab only adds domain code on top of:

| Need | Shared piece | Doc |
|---|---|---|

| tools on MCP servers | `McpGateway`, `MockManagedIdentityCredential` | [mcp-gateway](components/mcp-gateway.md) |
| block and validate tool calls | `deny_tools`, `retry_tool`, `validate_tool_result` | [middleware-and-hitl](components/middleware-and-hitl.md) |
| model access | `ZonePolicy`, `FoundryWriter` | [foundry-access](components/foundry-access.md) |
| retrieval, streams, explanations | `HybridIndexStandIn`, `EventHubStandIn`, `DataLakeStandIn`, `explain.contributions` | [search-and-streams](components/search-and-streams.md) |
| graph nodes and human review | `LabNode`, `RunState`, `Decision` | [middleware-and-hitl](components/middleware-and-hitl.md) |
| pass/fail and traces | `evals.gate`, `tracing.span` | [evals-and-tracing](components/evals-and-tracing.md) |

## 3. Build a lab, step by step

1. **Write the gold set first.** Put synthetic cases in `labs/<lab>/evals/gold/` and a generator in `labs/<lab>/data/gen_fixtures.py` so the data can be rebuilt.
2. **Model the contracts.** Pydantic models in `src/<pkg>/models.py` for every packet that crosses a node boundary, including the review packet a human sees.
3. **Expose systems as MCP servers.** One server per system, one app role per tool class, registered with the lab's `McpGateway`.
4. **Compute in code.** Risk scores, plans, clause matches and diagnoses are plain Python (NetworkX, scikit-learn, numpy). Agents call them as tools.
5. **Wire agents with middleware.** Every agent gets `deny_tools` for side-effecting tools and `validate_tool_result` for structured tools.
6. **Let the model write, not decide.** Use `FoundryWriter` with a `check` that compares the output with the computed facts.
7. **Assemble the graph.** Nodes subclass `LabNode`; the last node requests a `Decision` from a named reviewer.
8. **Gate it.** `evals/run_eval.py` computes domain metrics and calls `gate`; add the thresholds to the lab's `card.py`.
9. **Write the infrastructure.** `infra/main.bicep` and `infra/terraform/` with Data Zone deployments, managed identity and local auth disabled.
10. **Document it.** The lab README follows the 17 sections; outputs and code excerpts are generated by `scripts/doc_drift.py` so they cannot drift.

## 4. Checks that must pass

| Check | Command |
|---|---|
| lint and format | `ruff check . && ruff format --check .` |
| agent cards match code | `python scripts/export_agent_cards.py --check` |
| no secrets | `python scripts/secrets_scan.py` |
| docs match code and output | `python scripts/doc_drift.py --check` |
| tests | `pytest -q` |
| eval gates | `python scripts/run_all_evals.py` |
| Bicep compiles | `for f in labs/*/infra/main.bicep; do bicep build "$f" --stdout >/dev/null; done` |

## 5. Moving a lab to Azure

The order that keeps risk low:

1. Provision with Terraform or Bicep in a dev subscription ([deployment.md](deployment.md)); keep `DEPLOY_ENABLED` off until OIDC and environments exist.
2. Replace `FoundryChatClientStub` with the Foundry chat client using `ManagedIdentityCredential`.
3. Replace search, stream and lake stubs one at a time; keep the stand-ins for tests and evals.
4. Run the MCP servers remotely and swap the in-process client for streamable HTTP with bearer tokens.
5. Turn on the Azure Monitor OpenTelemetry exporter.
6. Re-run every eval gate against the deployed adapters before anyone relies on the output.
